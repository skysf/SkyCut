## 没到线的四处，为什么

1. **Codex 找工具打印的总字数 −24.8%（要求 ≥ 30%）**。条目本身短了三分之一（每个 853 → 573 token），但这条线量的是「打印出来多少字」，它被两件事顶住：
   - 全打一遍的那一次被 Codex 截在约 1 万 token（约 4 万字），条目再短也是 4 万字，只是这一屏多看到 5 个工具。8 个任务里还有 5 个第一步全打，这 5 次就是 20 万字。
   - 第一屏看到的条目多了、之后又按名字取，打印的条目总数没少（总说明的份数 161 → 206）。
   不全打的那 3 个任务降了 34–63%，过线。要整体过线，得让模型第一步不全打（8 个任务里现在有 3 个照总说明的「Start: get_status, get_settings, skycut_guide」只取了这三个），这是模型的习惯，SkyCut 这边只能靠总说明和名片引导。
2. **重复总说明占 43.7%（要求 ≤ 30%）**。Codex 给每个条目都背一份整份总说明（1,115 字），名片越短，它占的比例越大：小工具的条目现在约 1,900 字，总说明就占六成。
   试点报告已经算过：要 ≤ 30%，总说明得短到约 650 字。绝对量是降的：323,932 → 229,690 字（−29.1%）。这条线和方案自己的估算（迁移完每个条目约 2,170 字、总说明约 1,011 字，占 47%）对不上。
3. **第一次请求里 SkyCut 是 67 token，不是 0**。Codex 0.167 在开发者消息里给每个 MCP 服务器列一行、带总说明开头的 265 字，基线就是 64；
   这一行的长度没变（265 字），多的 3 个 token 是开头换了说法。方案的「仍是 0」是按 0.166 以前的记录写的。
4. **Claude Code 任务 6 被拒 1 → 2 次**。两次都在下一次调用改对，其中一次是基线里没见过的错法（把曲库 id 交给 `listen` 的 `file`）。
   同一个任务 Codex 是 3 → 0；两个客户端加起来，8 + 8 个任务被拒 5 → 2 次。

另有一条过了线、但留意：**整份预先加载 −7.6%**，`change_voice` 合进来之后估计在 −5.7～−5.9%（见上）。

3. **Codex 读 generate_media 仍然读全六节**。可以试着让第一次回答更短、把「报价再问只读 spending」放在最前面；或者接受 —— 它这一场的输入和基线持平。
