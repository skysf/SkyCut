## 〇、先说结论

1. **现在的账**：58 个工具，全清单（`tools/list` 的 JSON）**106,306 字**，上限 110,000，只剩 3,694；总说明 **2,012 / 2,048**，只剩 36。按仓库现用的估法（3.6 字一个 token）约 **2.95 万 token**。其中**工具说明只占 28%**（29,674 字），**参数定义占 60%**（64,306 字），每个工具的外壳（工具名、两份标题、注解）占 11.5%——其中约 9 千字（标题、注解）是客户端拿去分组放行的，**不进模型**。
2. **「每一轮整份清单发给模型」在两个主力客户端上已经不成立**，仓库里有两条认识过时了：
   - **Claude Code** 默认开工具搜索：一轮里常驻的只有总说明和工具名（约 1 千 token），某个工具的完整定义用到才加载。截断上限也已经改了：2.1.296 起总说明和预先加载的工具说明是 **4,096**，按需加载的工具说明是 **16,384**（官方文档；本机是 2.1.319）。2,048 只对旧版本成立。
   - **Codex**（本机 0.147 起，GPT-5.6 以后的模型）走「代码模式」：SkyCut 的工具**不在初始提示里**，模型在 `exec` 里筛 `ALL_TOOLS` 自己找。2026-10-26 报告说「每次调用 2.7 万 token 是因为整份清单每轮都发」，和同一场的原始记录对不上：第一次请求只有 **16,444** token，后面涨到 8.8 万是对话越来越长。
3. **真正的开销在别处**（本机 Codex 记录实测）：
   - Codex 给**每一个**工具条目都附上**整份总说明**，再附一段由参数定义转成的 TypeScript 声明。2026-11-03 那批真 Codex 会话，第一步全是「把 SkyCut 的工具都打出来」，输出被截在约 1 万 token，**只看到 55 个里的 11–12 个**；每场找工具共打印 5.3–15.7 万字，其中 **32–59% 是重复的总说明**。这些输出留在对话里，之后每次请求都带着。
   - Codex 把超过 5,000 字节的参数定义的说明**全部删掉**：`edit_clip` 在 Codex 里只剩 54 个光秃秃的字段名，那 2,800 字参数说明模型从没看到过。
   - 不按需加载的客户端（Claude 桌面版待实测、关掉工具搜索的 Claude Code 等）每轮还是整份，约 2.7 万 token。
4. **新设计**（第二节）：
   - 每个工具一张**名片**（≤450 字）：做什么（带用户会说的词）、什么时候用 / 不用、关键参数、花不花钱 / 要不要确认 / 几步撤销 / 回不回任务号；该先读说明书的写一句「Read skycut_guide topic=…」。
   - 一个只读、免费、不碰工程的**说明书工具 `skycut_guide`**：不带 topic 回一页**全部工具的地图**；`topic=<工具名>` 回那个工具的完整用法（字段、限制、例子、坑）；另有 rules / conventions / paid / workflows / errors 五个通用主题。一次最多 6,000 字，长的分节取。照 `recipes` 的路子在 App 里答（不排队、不摆窗口），在 Claude Code 里标 `anthropic/alwaysLoad` 省掉一次搜索；没开通时也照答，和 `get_status` 一样（名字和放行已定，第八节第 5 条）。
   - **总说明**从 2,012 字缩到约 1,000 字：开头几步 + 「先读说明书」+ 几条要 AI 主动做的规矩；按需求分组的工具目录搬进说明书首页（已定，第八节第 1 条）。
   - **参数定义完整保留**（名字、类型、枚举、必填、范围一样不少），只把参数说明压到 ≤120 字，并把范围写成数字（Codex 看不到 `minimum` / `maximum`；现在 154 个带范围的参数里有 69 个说明里没写数字）。
5. **防乱用不靠 AI 自觉读说明书**（第三节）：必须遵守的事要么服务器强制（参数核对、确认码、积分硬上限、一步撤销），要么写在名片 / 结果里；说明书只管「怎么做得好」；所有报错都指向对应的说明书。不建议「没读说明书就不让用」的硬门槛。
6. **新上限**（第四节；已定，第八节第 2 条）：全清单 110,000 → **100,000**；总说明 ≤1,200；名片 ≤450；参数说明 ≤120；单个工具的参数定义 ≤4,500 字节（`edit_clip`、`generate_media` 先列例外）；说明书每次 ≤6,000 字（硬限 8,000）。按 SC 4.10 的名片样稿重估后，迁移时的目标收紧到名片约 350、参数说明约 80，硬限不变（1.6）。
7. **迁移**（第五、七节）：**先做这件事，再加声音的 3 个工具**（已定，第八节第 3 条），**分批搬**（已定，第 4 条）。7 个 PR：说明书工具 → 地图和报错指路 → 试点 5 个最大的工具并用真客户端小测 → 两批搬完 → 收紧上限、改文档 → 连接 Codex 时放宽参数定义的字节上限（已定，第 6 条；先实测再合）。
8. **8 条拍板已定**（2026-11-09 用户确认全部按建议，第八节）：目录搬进说明书、新上限一组、先于声音、分批、`skycut_guide` 且没开通也照答、连接 Codex 时写字节上限、说明书只写英文、验收用用户额度且每次开跑前再问。

**预计效果**（按样稿和截断模拟估的，第六节实测为准）：

**这对清单大小意味着什么**：

- **Claude Code**：全清单总长几乎不影响它的每一轮。影响它的是三样：总说明（每轮都在）、单个工具的定义（第一次用时加载一次，之后随历史走缓存）、说明的前 4,096 字（搜不搜得到）。只有关掉工具搜索时才整份预先加载；`ENABLE_TOOL_SEARCH=auto` 时整份不到上下文 10% 也会预先加载（SkyCut 约 2.7 万 token，在百万上下文的模型上就会）。
- **Codex**：每轮的固定开销里 SkyCut 是 0；开销变成「找工具时打印了多少」，而每打印一个条目就多一份总说明。所以在 Codex 里，**总说明每多 100 字，就是打印的每个条目都多 100 字**。
- **整份客户端**：全清单就是每轮的开销，这时参数定义（60%）是大头。

## 二、新设计

### 2.1 什么放哪：三层变四层

现在的规矩（`ai-control-mcp.md` 第一节第 6 条）是三层：① 总说明 = 目录，② 工具说明 = 那一章，③ 出结果那一刻才用得上的写在结果里。改成四层，多出来的是说明书：

| 层 | 放什么 | 多长 | 谁、什么时候读到 |
|---|---|---|---|
| ① 总说明 | SkyCut 是什么、开头几步、「先读说明书」、几条要 AI **主动**做的规矩 | ≤1,200（前 512 字自成一体） | Claude Code 每轮；Codex 每打印一个条目带一份；整份客户端每轮 |
| ② 名片（工具说明） | 做什么 / 什么时候用 / 关键参数 / 花钱·确认·撤销·任务号 / 要不要先读说明书 | ≤450 | 用到这个工具时（Claude Code 加载它、Codex 打印它）；整份客户端每轮 |
| ②′ 参数说明 | 一句话含义 + 单位 + 范围（数字）+ 默认 | 每条 ≤120 | 同名片；Codex 里参数定义超过 5,000 字节时看不到 |
| ③ 说明书（`skycut_guide`，新） | 工具的全部用法、例子、限制、坑；通用规矩；常见流程 | 每次回 ≤6,000 | AI 想读时；名片要求先读时；报错指过去时 |
| ④ 结果 | `next_step`、`needs_confirmation`、`waiting_for_user`、`voice.note`、任务的「用 get_job 等」…… | 不变 | 出结果那一刻 |

往总说明里加东西之前先问「是不是要 AI 主动做」，这条照旧；新加一问：**往名片里加东西之前先问「不知道这件事会不会调错 / 花错钱」**，不会的就进说明书。

### 2.2 名片

**写什么**（固定顺序）：

1. 第一句：动词开头说做什么，带用户会说的词（9:16、水印、配乐、口头禅……）。Claude Code 的搜索只看说明的前 4,096 字、Codex 的模型拿正则筛名字和说明，搜不搜得到靠这一句。
2. 什么时候用 / 不用，和长得像的工具怎么分（`edit_clip` / `edit_clips` / `add_clips`）。
3. 关键参数：从哪来（`clip_id` 来自 `get_timeline`），最容易错的一条语义（时间线秒还是素材秒）。
4. 按工具性质必写的固定说法（守卫查）：只读 → `Read-only`；改工程 → `One undo step`；长任务 → `Returns job_id; wait with get_job`；花钱 → `Paid (Sky Studio credits)` + 报价 / 确认 / 每日硬上限；会问 → `needs_confirmation`；删文件 → `Trash`。
5. 要先读说明书的工具，最后一句「Read skycut_guide topic=<工具名> before the first call」。哪些要：花积分的（`generate_media`、`upscale_clip`、`manage_characters`、声音的 `add_voiceover` / `manage_voices` / `change_voice`；只读免费的 `list_voices` 不要）、流程长的（`record_screen`、`sync_voiceover`、`cut_speech`）、参数多的那一部分（`edit_clip` 的取景 / 区域 / 声音）。其余工具不写，省字——总说明里已经有一条通用的「名片要求时先读、调错了先读」。

**多长**：硬限 450，目标 350（按 SC 4.10 的样稿重估后从 400 收紧，不然全清单会超 100,000，见 1.6）。理由：整张名片落在前 512 字里，本身就自成一体；最复杂的两个工具按上面的格式写下来是 443 / 442 字（下面的样稿），简单工具本来就短（`cancel_job` 58、`seek` 93）。

**样稿**（英文，给 AI 的字只用英文；括号里是字数）：

- `edit_clip`（443）：`Change one clip: trim (source_in/source_out, source seconds), speed, volume/fades, crop, reframe for 9:16 (fit=fill), region={x,y,width,height}, position/scale, entrance/exit, file swap. Batch: edit_clips; new clips: add_clips. clip_id from get_timeline. Trim: the timeline start stays, the end moves. One undo step; invalid values change nothing and return allowed values. Before framing, region or sound fields: skycut_guide topic=edit_clip.`
- `generate_media`（442）：`Paid (Sky Studio credits): image, video, lipsync, cutout, music or sound effect from a prompt or files; never edits the timeline (import with add_clips; video upscale: upscale_clip). Returns job_id; wait with get_job. quote_only=true prices without spending. Over-plan requests return needs_confirmation: ask, then repeat with confirm_token. The daily credit limit always applies. Read skycut_guide topic=generate_media before the first call.`
- `look`（390）：`Read-only. See frames instead of guessing: the composed timeline (time/times, or count across clip_id) or a file (source seconds). Returns a labelled contact sheet plus boxes for faces/people/text, brightness and black bars. Also: files (up to 24 files), shots=true (shot bounds), text_scan=true (burned-in subtitles, watermarks). Long scans return job_id. Details: skycut_guide topic=look.`
- 声音的四张以 SC 4.10 的样稿为准（UTF-16 实测）：`add_voiceover`（439）、`list_voices`（276）、`manage_voices`（401）、`change_voice`（337）。花积分的 `add_voiceover`、`manage_voices`、`change_voice` 末尾写「Read skycut_guide topic=… before the first call」；只读免费的 `list_voices` 不写。

样稿保留了现有守卫要求的短语（`edit_clip` 的 `timeline start stays`、前 512 字里的 `region={x,y,width,height}`）。`generate_media` 现在被要求的 15 个词里，`MiniMax H3`、`image_to_video`、`library`、`camera_angle`、`upscale` 是「怎么用好」，搬进说明书（5.2）。

### 2.4 总说明：从「目录」变成「入口 + 主动规矩 + 怎么读说明书」

- Use only SkyCut tools and given/returned files: no ffmpeg, scripts or terminal on media; never download media; say when a capability is missing.
- Follow get_settings permission mode and conversation language.

- undo round=true reverts this round; report project_saved_to.

- 搬走的：「Tools by need」那一大段（按需求分组的全部工具名）→ 说明书地图。理由：Codex 每个条目带一份总说明（1.4：重复占 32–59%）；Claude Code 已经单独把工具名列给模型（官方：会话开始只加载工具名和总说明），2026-09-30 定「每个工具名都要在目录里」时的理由（开搜之前只知道目录里写的）现在由「工具名本来就在 + 地图一次读全」接住。这条改了用户 9-30 拍的板，2026-11-09 用户已确认（第八节第 1 条）。
- 留下的：四条老规矩原样；新加两条（结果里叫做什么就做什么；名片要求时、调错之后先读说明书）。
- 总说明只在握手时给（10-14 案例 `docs/bugfixes/2026-10-14-stale-helper-tool-list.md`）：升级 SkyCut 之后重开 AI 会话就是新的。只有用户本人在用，不为旧会话做过渡。

### 2.5 参数定义：完整保留，说明缩短

1. **每个参数照旧有**：名字、类型、枚举、必填、范围。客户端靠它校验、模型靠它拼调用，`MCPArgumentCheck` 靠它挡错名字。**不做**把少用参数塞进自由对象（`additionalProperties: true`）的「省法」：会改掉调用的形状、打破剪辑风格卡里引用的参数名（`RecipeChecks` 钉着）、也违背「参数定义要完整」。批量三件和 `film` 是已有的例外，不扩大。
2. **参数说明 ≤120 字**（目标 ≤80，按 1.6 的重估从 100 收紧）：一句话含义 + 单位 + 范围 + 默认。现在 562 条里 548 条已经 ≤120，要改的是 14 条长的（多出来的话搬进说明书那一节）。
3. **带范围的参数，范围写成数字**：Codex 把参数定义转成 TypeScript 时不显示 `minimum` / `maximum`（实测 `get_job.wait_seconds` 的 0–30、`set_text.font_size` 的 12–1000 都看不到），现在有 69 个参数的范围只在 schema 里。补上约 700 字。
4. **相互影响、例子、为什么、边角情况** → 说明书那个工具的对应一节；**跨工具的约定**（时间线秒 / 素材秒、V1 / A1、短 id、x / y 是比例、`project` 的 p1…）→ `conventions` 主题，参数里只留短的那一半。
5. **单个工具的参数定义 ≤4,500 字节**（Codex 默认 5,000 字节就删光参数说明，留 500 余量）。`edit_clip`（6,662）和 `generate_media`（6,556）去掉全部参数说明后的骨架还有约 2,700–2,900 字节，剩下 1,600–1,800 字节要装 57–58 条参数说明，每条正文只剩十几个字，压不进来：先列例外，它们在 Codex 里本来就只有名字和类型，所以**它们的名片要带上会影响调用对错的语义**（样稿里的素材秒、裁切语义、报价 / 确认）。已定（第八节第 6 条）：连接 Codex 时给 skycut 那一节写 `tool_input_schema_max_bytes = 8192`（PR 7），先在本机 0.166 / 0.167 实测这个键被接受、两个工具的注释回来了才合；实测不行就不写，这两个工具仍靠名片 + 说明书。自己手动配 Codex 的用户仍是默认的 5,000，所以 4,500 的上限和例外名单照留。

## 三、怎么防止 AI 不读说明书就乱用

### 3.1 依据

| 发生过的事 | 说明了什么 |
|---|---|
| 2026-09-30：Claude Code 至少从 9-29 起只读到总说明的前一半，后面的规矩一句没读到；没有一个用户报过由它引起的错——因为大多数规矩也写在工具说明或结果里 | 规矩放在**用的那一刻看得到的地方**才可靠；只写在一份长文里的不可靠 |
| 2026-10-26：真 Codex 给 `set_text` 传了不存在的 `end`，SkyCut 悄悄丢掉；修法是服务器核对参数名（`MCPArgumentCheck`），不是把说明写得更好 | 换一个客户端就会冒出新的错法；**能挡的要在服务器挡** |
| 2026-10-31：Codex 里 `edit_clip` 的 2,800 字参数说明一条都没给模型 | 写了不等于读到；会影响对错的语义要在名片里 |
| 2026-11-03：目录短、批量 / 同步 / 检查 / 导出各带一行能过 schema 的例子，真 Codex 四个需求都选对了工具；测试脚本自己写错的 `size` 被参数核对挡下；结果里建议的不存在的 `end` 被找出来改掉 | 例子和结果里的提示也是接口，要守卫；参数核对兜得住 |
| 11-03 四场：模型第一步都是把工具全打出来，并且打印条目才能看到参数声明 | Codex 的模型**一定会读名片**（不读拿不到参数声明）；说明书是多跳一步，可能跳过 |
| Claude Code 官方：「put critical details near the start」；搜索只看说明的前 4,096 字 | 名片前部写关键的 |

### 3.2 判断

- **不能指望 AI 一定读说明书**。设计成：跳过说明书只会让活做得没那么好，不会做错事、不会多花钱、不会删错东西。
- 所以：会做错 / 花错钱 / 删错的 → 服务器强制，或写在名片和结果里（2.6）；怎么做得好 → 说明书。
- 读说明书的成本不高（每次 ≤2 千 token），但不该被强制：服务器验不了「读懂了」，强制只会多一跳。

### 3.3 做法

1. **报错指路**（两处，都只改一个地方）：
   - `MCPArgumentCheck.message`：末尾加「Fields and examples: skycut_guide topic=<工具名>.」
   - 路由里 `catch let error as AIToolError` 那一处（`AIToolRouter`）：给工具的报错统一加一句「Guide: skycut_guide topic=<工具名>」。现在 `AIToolError` 有约 430 处抛出，不逐个改。
   - 规范支持：2026-07-28 版要求把参数校验这类错误作为工具结果（`isError: true`）交给模型，「to enable self-correction」——我们本来就是这样。
2. **名片里必写的固定说法**（2.2 第 4 条）由守卫按工具性质检查。
3. **要先读的工具，名片最后一句明说**（2.2 第 5 条）。
4. **结果里的 `next_step` 不变**（第四层）。
5. **量**：验收时记下每个任务读没读说明书、读的是哪一节、是不是第一次用之前读的、报错后是不是读了再改对（第六节）。先不设门槛，用数据决定下一步要不要把哪句挪进名片。

### 3.4 不建议的做法

| 做法 | 为什么不 |
|---|---|
| 没读过某个工具的说明书就拒绝执行（硬门槛） | 服务器验证不了「读懂了」；每个工具多一跳；要在 App 里按会话记读过什么；花钱的流程已经有报价 → 确认 → 硬上限这道真门槛 |
| 每个名片都加「Guide: skycut_guide topic=…」 | 58 × 约 35 字 ≈ 2 千字，常驻；总说明里一条通用规矩就够了，只给真要先读的工具加 |
| 把说明书内容塞回结果 | 结果是「那一刻用得上的」，塞多了每次调用都背着 |
