## 一、为什么要短

AGENTS.md 是唯一入口，每个会话一开就整份读进来。2026-11-13 之前每条索引都带一大段摘要：339 KB，光读它约 14.7 万 token，规则本身只有 11 KB；
收短之后约 100 KB。索引只负责让人找到文档，规矩以文档正文为准，细节留在正文里。

## 二、三类小节和上限（`checks/docs-index-drift.sh` 钉着）

| 小节 | 怎么写 | 上限 |
| --- | --- | --- |
| **索引小节**：AGENTS.md 的「规划与实施报告索引」「架构与长期约束索引」「根目录文档」，以后新加的「## 」小节也算；整份 `docs/bugfixes/INDEX.md` | 一条索引一行，只有一种写法：顶格的 `- [标题](路径.md) — 一句话`，一条正好一个链接。AGENTS.md 的索引小节另许成形的表格（表头 + 紧跟的分隔行，每行正好一个链接）；`docs/bugfixes/INDEX.md` 是纯列表。别的写法都红（第六节）。`docs/bugfixes/INDEX.md` 另有顺序：整份按文件名里日期后面那一段排、一份案例只列一次（第五节） | 每行 ≤ 400 字节；条目以外的行（开头的说明、小标题、表头）每节 ≤ 5 行 |
| **「Bug 修复案例索引」**（AGENTS.md 那一节） | 只留指路的话（普通的一行或 `- ` 开头的一行）；案例的条目只进 `docs/bugfixes/INDEX.md`：这一节里任何指向 `docs/bugfixes/` 下案例的链接都红（`INDEX.md`、`TEMPLATE.md` 除外），不管前面是什么记号 | 每行 ≤ 400 字节，≤ 5 行 |
| **不设单条上限的小节**：唯一入口约定、开始任务前、全局规则、文档目录职责、按修改范围选必读文档、构建与检查入口 | 前四节是规则本身；必读表一行 = 左列的检索线索 + 右列的链接和一两条硬约束；检查入口每个脚本一行 | 只受整份上限 |

1. **必读表和检查入口有意不设单独的预算。** 必读表一行要带一串检索线索和几份文档的链接，按条数或每行设上限只会逼人删左列的检索词
   （复审的 F2 就是这样丢的）。它们和别的小节一起只受整份上限约束。
2. **整份上限** = 71,000 + 250 × `docs/bugfixes/` 以外的文档数（只数普通文件）。多一份文档多一条索引是应该的，所以上限跟着文档数走；
   Bug 案例不往 AGENTS.md 里加行，不算进文档数，它们在必读表里加的链接从基数的余量里出。
3. **超了怎么收**，只有两种，都不抬 400、71,000、250 这几个数：
   - 摘要挪进它指向的文档：必读表右列只留链接和一两条硬约束，检查的细节挪进[检查细目](../testing/check-catalog.md)；
   - 撤掉必读表里的旧案例链接，但**只许撤这一种**：同一行链着的架构文档已经写了那条规矩，并且那份架构文档里链着这份案例。
     案例本身照旧留在 `docs/bugfixes/INDEX.md`（用户 2026-11-13 定）。规矩只写在案例里的、架构文档没链那份案例的，都不许撤。
4. 改了小节的标题，要同步改守卫里的名单（`checks/docs-index-drift/config.sh` 的 `FREE_SECTIONS`、`POINTER_SECTION`、`INDEX_SECTIONS`）；
   守卫会先说找不到它，不会悄悄换一种管法。三个索引小节的标题也在名单里：去掉标题，下面的条目就并进上一节。

## 三、收成一句话时不能丢的（守卫查不到，对着正文自己查）

守卫只量形状和字节，一句话说反了它不知道。收短、改写一条索引或必读表的一行之后，逐条对着它链着的文档读一遍，照下面几条查：

1. **带「只有 / 一律 / 永远 / 从不」的句子**：要么把例外写全，要么只写话题、把规矩留给正文（例：「什么时候问用户按权限模式和第四节第 6 条」）。
   省略号不算交代了例外。复审撞上的：「只有删文件才问…」把读别处的文件、偏离已授权的规格、声音的授权和一次性费用都删了，和 AI 接口第四节第 6 条相反。
   没写「只有」、口气是绝对的也算：全量复查撞上「不认识的参数名整个调用不做」（null、`project`、自由对象、登记的别名照收）、
   「中日文只在词和词之间断」（比一整行还宽的词拆字）、「占着就往上抬一轨」（只有画面，声音是反的）、「只收 CC-BY / CC0」（用户自己的 `owned` 也收）。
2. **实测数字带着它的条件**：哪个客户端、哪个构建（几个工具）、缓存冷还是热、原样重跑还是真 PR、谁按什么放行。不同次量出来的数不拼进同一句，
   「过线」只写真过了的那一方、那几条线。复审撞上的：61 个工具时的 −7.6% 和加进第 62 个工具后补量的 −6.7% 被拼成「61 个工具、−6.7%」；
   试点只有 Claude Code 过线，Codex 三条数值线没到、是协调者按结果放行的；「约 6 分钟」是缓存热、原样重跑的数。
   不是数字的实测结论同样：只在某个条件下成立的写上条件（「`listen cuts` 和 cut_speech 一致」只在同一份完整转写下，局部转写差一帧）；
   没验到的别写成「全流程」「跑通」（工具回的状态对了不等于界面目检过；那份报告自己把「真的一个窗口都不开」列在没验到里）。
3. **修法的适用范围和前提写明**：只在一个入口生效的修法写出是哪个入口，别写成泛指 —— 泛指的那句会和另一份长期合同撞上。
   复审撞上的：「换格子显式取最近的 1/600」其实只管原生抽帧的请求，合成的时间照旧截断（[预览自由变换](preview-free-transform.md)）。
   算法只在某个前提下成立的，前提也是规矩的一部分：定格只拿掉帧率已知、后面没接转场的不到一帧的右半；压黑 / 闪白只在两侧盖满且不透明时照 xfade 算；
   鼓点只在请求落在前 15 分钟里时共用整段分析。同一个修法在某个入口只做了一半的（官方原创短片的越档只查带没带原话、不查规格名），也要写出来，
   别让一句话把它包进去。
4. **必读表的左列是检索线索，不是摘要**：类型名、参数名、端点、注解从左列删掉之前，想想别人改它时会搜哪个词；挪到右列不算丢，整行都没了就算。
   已经去掉的东西留一个「`clone_from` 的移除」这样的标签，别写回成现有的能力。
5. **后来被改掉的做法、过期的状态**：文档里的做法后来被另一次修复或拍板废止了（同文后面的「更正」「补充」、后来的案例），索引写现行的，
   或者写明「某日已移除」，别把废止的写成现行规矩。「进行中」「第一轮」「还没上线」这类状态带上截至哪天。
   全量复查撞上的：「真人拒绝只在退款明确后替换一次」10-31 已整个移除；联动方案的「真删才连带删」10-15 起对字幕不成立；第五块报告还写「进行中 / 第一轮」。
   正文里同样过时的句子补「截至某日 / 后续已改」的注记，不改写当时的事实和实测。
6. **会漂的计数**：「用户拍的 58 条板」这种总数，正文往表里加一条就不对了（方案后来加到第 60 条）。总数不是要点就别写；要写就带上截至哪天。
7. **相对的指代**：「上一条的横向孪生」在索引重排、中间插进新条目之后就指错了（`docs/bugfixes/INDEX.md` 按文件名里日期后面那一段排，「上一条」是谁由文件名定，不由写的人定）。
   写出指的是哪一份（日期 + 标题），或者把那句意思直接写出来。
8. 拿不准怎么概括，照抄正文的说法，或者只写话题。「链接都还在」只证明找得到，不证明没说反。

## 五、并行的 PR 别撞在同一行（2026-11-13）

几件事同时开着时，后合的 PR 常常变 DIRTY：得把 main 合进去、再等一轮 CI（CI 同时能跑几个见[构建与打包](../build/build-and-packaging.md)「CI」一节）。
2026-10-15 到 11-13 合的 200 个 PR（#205–#407）里，分支上「把 main 合进来」的合并有 55 次真解过冲突（32 个 PR），37 次是在 PR 开着以后；
撞得最多的是 AGENTS.md（31 次，其中 14 次在当时还在它里面的 Bug 案例索引）。

1. **Bug 案例索引整份按文件名里日期后面那一段的字母序排，不看日期**（用户 2026-11-13 定）：`2026-11-13-index-entry-limit-bypassed.md` 看的是
   `index-entry-limit-bypassed.md`。字节序（`LC_ALL=C`），从小到大；这一段相同的再按日期；模板那一行留在最上面。
   新案例按这一段插；插错了守卫会说该排在谁上面。
   - 为什么不按日期：同时开着的两个 PR 写的多半是同一天的案例，按日期排它们总往同一处加。那 200 个 PR 里 88 个加过案例索引，两边各加了一行的合并 15 次
     （14 次两边的案例是同一天的）。拿这 15 次重放：都加在模板那一行下面（最早的做法）撞 14 次；按文件名从大到小（同一天上午的做法，PR #413）还撞 5 次 ——
     新的一天的头两条必撞；按日期后面那一段排 0 次。
   - 代价：索引不再从新到旧。找案例是按关键词搜的，日期每条自己带着（守卫查条目的文字以文件名里的日期开头），所以没有损失。
     「规划与实施报告索引」没改：那里从新到旧有用。
   - 还会撞的只剩一种：两条新案例的那一段正好紧挨着、中间没有别的条目（`git merge-file` 模拟：中间隔着一条已有的就不撞）。
     撞了照样解：两行都留、按规矩排好，再跑 `scripts/check-local.sh docs-index-drift`。
   - 守卫查顺序，顺带查同一份案例列了两次（解冲突时两边的改动都留下了）；换一种路径写法（`./x.md`）、写进表格都不算另一份。
2. **哪份文件都不用 `merge=union`，仓库里没有 `.gitattributes`。**
   - GitHub 不认它：PR 的「能不能合」、合并按钮、Update branch 都照样算冲突。2026-11-13 实测（#409–#412，用后就删的分支）：给测试文件设了
     `merge=union` 的一组和没设的对照组一样，合掉第一个 PR 之后第二个都是 CONFLICTING / DIRTY，合并回「Pull Request has merge conflicts」；
     nix-rust/nix 从 2017 年起在默认分支上给 CHANGELOG.md 设了它，PR 照样撞（GitHub 社区讨论 #9288，到 2026-10 还没有回应）。
   - 本地的 `git merge` 认它：本地合得进、GitHub 上还是 DIRTY，两边说法不一样；它把两边的行按「先 main 后分支」拼，会打乱第 1 条的顺序；
     同一行两边都改过时两个版本都留下、不报冲突。
   - 所以就算以后 GitHub 认了，AGENTS.md、带数字的基线（`checks/source-file-size-baseline.txt`、性能基线）、脚本和代码也不许设；
     只有「每行各自独立、只加不改、顺序无所谓」的清单可以考虑，而且要先有守卫查重复。
3. **AGENTS.md 里还会撞的**（Bug 案例索引搬走以后剩下的）：必读表的同一行（两个 PR 往同一行加链接，两边都改了同一行）、规划与实施报告索引的最上面、
   架构索引的同一行。这些靠排序和 union 都治不了：
   - 改索引行、必读表的那几行放进最后一个 commit；开 PR 之前 `git fetch`、再合一次 `origin/main`（「合并与分支」本来就要求）。
   - 撞了：两边的改动并进同一行，别留两行；改完跑 `scripts/check-local.sh docs-index-drift`。
   - 要改必读表同一行、同一份架构文档同一节的几件事，交给同一个会话按顺序做，或者等前一个合了再开 —— 这是排任务的时候定的。

## 六、两份索引里许写什么、不许写什么（白名单，2026-11-13）

守卫以前是「认出不许的写法才红」，一天里被绕过三轮：每一轮都是换一种 Markdown 里合法的写法，守卫认不出就当没看见
（[案例](../bugfixes/2026-11-13-index-entry-limit-bypassed.md)和它的两段「后续」）。现在反过来：AGENTS.md 和 `docs/bugfixes/INDEX.md` 里
**只许出现下面这几种写法，别的一律红，并说出是哪一行**。两份文件 2026-11-13 时一处例外都没有，所以没有豁免名单。

**整份文件**（不设单条上限的小节也算）：

| 许写的 | 不许的 | 为什么 |
| --- | --- | --- |
| 链接只有一种：`[字](相对路径.md)`，可以带 `#锚点`。路径只用字母、数字、`.` `_` `-` `/`，`../` 只许写在最前面 | 引用式链接和它的定义、`<a href>`、图片、带标题或尖括号的链接、`./`、以 `/` 开头、网址、不是 `.md` 的目标、没有看得见的字的链接文字（至少要有一个字母、数字或汉字，行内代码里的也算；只有空格、细空格、盲文空白这类空白的不算 —— 正着认，不往黑名单里补空白） | 漏索引和死链用同一套提取。守卫不认的写法，它查不了死链，也不该算索引 |
| 方括号只用在链接里；正文里要写就放进行内代码 | 脚注、任务框、套在链接里的链接、正文里的方括号 | 剩下的方括号都「可能是另一种链接」，一律不猜 |
| 行内代码：一对反引号、不跨行、不是空的 | 代码围栏（反引号或波浪线，套在引用、列表里的也算：一行里有连着的两个反引号或三个波浪线就红）、不成对的反引号 | 围栏和行内代码里的路径看着像索引，其实点不开 |
| 普通的字 | 行内代码以外的 `<`（HTML、注释、自动链接）、反斜杠、`$`、HTML 实体；制表符、回车和别的控制字符；零宽空格、不换行空格、全角空格、文字方向控制符 | 它们都能让一个链接看着在、其实看不见或点不开 |
| 第一行是 `# 标题`；缩进的行只接在列表项后面；列表记号后面只空一格 | 开头的 front matter；空行、标题、表格、普通段落后面缩进的行；记号后面空好几格 | 这些位置上的内容渲染成代码块或元数据，不是正文 |

**`docs/` 下的文件**：文档只许是普通文件、后缀小写的 `.md`、路径只用字母、数字、`.` `_` `-`（所以链接不用去支持括号和空格）。叫 `xxx.md` 的文件夹不算文档；
符号链接、`.MD` / `.markdown`、名字不合规的都红。`docs/bugfixes/` 下只放 `YYYY-MM-DD-<slug>.md`、`TEMPLATE.md`、`INDEX.md`，不建子文件夹。
漏索引、死链、算整份上限用的是同一份清单；路径大小写也要一字不差。

**不设单条上限的小节**只多一条：列表项不许以链接开头 —— 那是索引条目的写法，条目放进索引小节才有每条 400 字节的上限
（规则里要提一份文档，把链接写在句子中间）。

**索引小节和整份 `docs/bugfixes/INDEX.md`**：

- 条目只有一种写法：顶格的 `- [标题](路径.md) — 一句话`，一条正好一个链接（一句话里不再链别的文档）。
- AGENTS.md 的索引小节另许表格：前面空一行，表头下面紧跟分隔行（列数一样、行尾都是 `|`），每一行正好一个链接。`INDEX.md` 是纯列表，不许表格。
- 条目以外只许空行、标题和条目前面的说明（说明不以链接开头）。别的列表记号、缩进的行、`>` 引用、分隔线、不成表格的竖线行、接在条目或表格后面的话都红。
- 同一份文档在 AGENTS.md 的索引小节里只当一次条目（带不同的锚点也算同一份）。这些小节和「Bug 修复案例索引」一节里不许链 `docs/bugfixes/` 下的案例
  （`INDEX.md`、`TEMPLATE.md` 除外），不管前面是什么记号。
- `INDEX.md` 的条目只列同文件夹的案例：链接写 `YYYY-MM-DD-<slug>.md`（不带路径、不带锚点），文字以文件名里的日期开头；
  说明里不许链案例 —— 只当条目列，才进顺序和重复检查。
