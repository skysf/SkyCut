# 2026-11-04 后台生成等待引擎时，短探测无限等输出且重复启动

## 症状

后台 MCP 验收中，新建的隔离测试 App 在官方生成的引擎前置步骤持续等待；
观察到同一个仓库引擎的三个 `-hide_banner -version` 子进程，超过 12 分钟仍未返回。
当时没有 `/jobs` 请求，也没有官方提交回执。改用已安装签名 App 的引擎后，同一流程走过了提交前置。
这证明了等待位置和可用替代路径，未证明具体 OS/TCC 拦截原因。

## 根因

`FFmpegRuntime.runCapturingOutput` 同步调用 `readDataToEndOfFile()` 和 `waitUntilExit()`，
既没有截止时间，也没有输出上限和退出码检查。短查询未退出时，后台调用者无法结束引擎等待。
`MediaToolchain.resolveIfNeeded` 只判断 `isResolving && runtime == nil`；定位任务挂起期间这两个条件
一直成立，其他入口能继续启动重复定位。定位还被放在 `Task.detached` 的协作线程中。

## 修复

新增窄用途 `FFmpegRuntimeProbe`：原生启动、非阻塞合流读取和父进程独占的非阻塞回收，
版本 / 滤镜两次命令共享单候选 5 秒预算、每条命令 256 KiB 总输出上限，并要求正常零退出。
滤镜查询失败也拒绝候选；正常无 libass 时仍如实发布能力。候选路径去重后保留原来源优先级。

失败仅停止自己的探测进程，TERM / KILL 各轮最多轮询 0.2 秒。只有本组件回收自己启动的 PID；
回收前才决定是否升级信号，避免把旧 PID 带到后来。若 OS 尚未交付退出，再交给一次事件回收，
不建永久等待线程。子进程不会继承无关文件描述符、标准输入或调用线程的信号屏蔽状态。
原生启动或内核本身不可中断的边界保留明确说明，不宣称绝对的 OS 时限。

MainActor 上同步登记一份定位任务，再把阻塞工作送到既有 `MediaReadQueue.analysis`。
保持原单例和私有初始化，不为自检新增可注入的公共定位 API。

## 教训 / 防回归

“只是查一下版本”也会成为后台工作的前置依赖。它必须限制时间和输出、检查退出结果，并在
异步入口合并重复请求。进程自身结束与管道 EOF 是两件事；批量自检的总时限也不能替代单项
工作截止时间。长期合同见[阻塞的媒体读取](../architecture/blocking-media-reads.md)。
