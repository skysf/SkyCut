# 2026-11-04 CI 的 .build 缓存从来没省下过一次编译

## 症状

- CI 第 1 组每一轮都把完整 App 冷编一遍：2 分 10 秒到 2 分 45 秒（PR #302：2 分 43 秒），是最慢那一组里最大的一块；第 2–5 组
  每组第一项检查先编核心库，又是 26–41 秒。可每一轮的日志都写着恢复了缓存（`Cache restored from key: swiftpm-macOS-…`）。
- 仓库里只有一份 `.build` 缓存：26.79 MiB，10-26 存的（仓库改名换了检出目录、key 变了的那一次）。之后每一轮都是
  `Cache hit occurred on the primary key …, not saving cache`。
- PR #302 第 1 组的冷编日志里，SrtFlow 639 个、SrtFlowCore 29 个文件全部重编。从 10-26 到那天，SrtFlowCore 的 39 个文件只改了 3 个。

## 根因

三个叠在一起，哪一个单独修了都不够：

1. **SwiftPM 看修改时间「和上次记下的一不一样」决定要不要重编，CI 每次 checkout 出来的时间都是那一刻。** 恢复回来的 `.build`
   里记的时间一个都对不上，于是全部重编。构建文档里早写了「多半是因为修改时间」，但一直是猜的，没人验、也没人修。
2. **key 只看 `Package.swift`。** 内容不变 key 就不变；`actions/cache` 命中主 key 之后不再存，缓存永远停在存下它的那一刻。
3. **五组共用一个 key。** 谁先跑完谁存，第 1 组最慢、从来轮不到。存下的是只编了核心库的某一组，所以才 27 MB，里面根本没有
   完整 App 的目标文件。

## 修复

- `scripts/ci-stable-mtimes.py`：checkout 之后、恢复和编译之前，入库文件的修改时间按内容（git 的 blob id，约 60 位进了秒和
  纳秒）算。内容没变的文件每次 checkout 都是同一个时间；变了的换一个时间。
- `.github/workflows/checks.yml`：取和存拆开（`actions/cache/restore` + `actions/cache/save`），每组一份；key 带检出目录、
  工具链指纹（`xcodebuild -version` + `swift --version` 的哈希，工具链那一步给出）、组号和这次的提交，restore-keys 去掉提交；
  只在 main 上、整组绿了才存。PR 恢复 main 上最新的那份。「Build app」那一步不再叫冷编。
- **安全前提**：内容变了的文件，按内容算出来的新时间多半比上次编译还早。SwiftPM 比的是「一不一样」，不是「是不是更新」，
  所以照样重编 —— 这一条要是不成立，缓存就会拿旧的目标文件测新代码、一路假绿，所以每一轮 CI 都真验一遍（下面）。

## 验证

- 小包实验（本机原生 arm64，和 CI 同一个 Swift 6.3.3 / swift-driver 1.148.6，三个文件的可执行包）：
  | 情形 | 重编几样 |
  | --- | ---: |
  | 什么都没改再编 | 0 |
  | 改了内容、修改时间拨回 2001 年（比上次编译早） | 3，跑出新值 |
  | 没改内容、只把修改时间挪到 2001 年 | 2（修改时间一变就重编，这就是 CI 的病根） |
  | 新 clone（新的 inode、新的修改时间）+ 放回 `.build`，不设时间（以前的 CI） | 4（全部） |
  | 新 clone + 按内容设时间 + 放回 `.build` | **0** |
- `scripts/check-ci-build-cache.sh`（第 4 组）每一轮 CI 在小包上照 CI 的样子真走一遍：改过的文件时间拨早了照样重编、跑出新值；
  新 checkout 按内容设时间、放回 main 的 `.build` 重编 0 样；新提交改了一个文件（PR 的样子）那个文件重编、跑出新值；对照组
  不设时间全部重编。反向验证：`ci-stable-mtimes.py` 把所有文件设成同一个时间 → 红（「重编了 0 样、跑出来是 OLD-VALUE-0001」，
  正是拿旧的目标文件测新代码）；`ci-stable-mtimes.py` 什么都不做 → 红（「重编了 4 样」）。本机原生跑 54 秒。
- `checks/ci-build-cache-key.sh` 扩成钉整套写法（取 / 存分开且 key 一字不差、key 的几部分、restore-keys、只在 main 上绿了才存、
  按内容设时间排在恢复和编译之前、工具链那一步给出指纹），保留原来「带检出目录」那一条。拿合并前的 workflow 喂给它：红。
- PR #307 自己的 CI 是冷的（五组都 `Cache not found`，PR 上不存）；小包检查在 CI 的 runner 上也绿了。合并后 main 那一轮（冷）存下五份：
  第 1 组 122 MiB、其余 19–27 MiB。原样重跑那一轮（第 2 次尝试）：五组都恢复了自己那份，App 和核心库 **重编 0 个文件**，
  「Build app」**2 分 12 秒 → 15 秒**（恢复缓存 6 秒），第 1 组 7 分 45 秒 → 5 分 52 秒，整轮约 6 分钟；第 2–5 组子脚本里编核心库那一笔
  每组 40–55 秒 → 13–28 秒。账见 [2026-11-04 一个 PR 要多久](../reports/2026-11-04-ci-speedup.md)。

## 教训 / 防回归

- **「缓存命中」不等于「省下了编译」**：验收看编译那一步花了几秒、重编了几个文件。
- **`actions/cache` 的 key 里没有会变的东西，命中之后就再也不存**；几个 job 共用一个 key，存下的是最先跑完的那个，不一定是最需要的那个。
- **写进文档的「多半是因为……」要么去验，要么在用到的地方说清楚这是猜的**。这次一个三文件的小包、几秒钟就验清楚了。
- 长期规矩写在 [构建与打包「CI」一节](../build/build-and-packaging.md)。
