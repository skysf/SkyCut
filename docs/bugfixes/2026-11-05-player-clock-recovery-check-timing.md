# 2026-11-05 声音恢复成功，播放器自检却因固定等待窗口报红

## 症状

PR #313 的 CI 全绿，合并到 main 的 `8fc38ec` 后，
[Actions 41987890219](https://github.com/skysf/SkyCut/actions/runs/41987890219) 的 player-clock 检查报告
`FAIL [line 77] 中断恢复后播放头继续向前`：63 项里只有这一项失败，其余四组、音频引擎和性能检查通过。

## 根因

合并提交与 PR 末提交 `1970a81` 的 tree 都是 `a488c8b93ae85a2a2c868f7bef8b78c1c39df733`，
合并没有引入内容差异。失败前一条「播放途中声音图停掉也会恢复」断言通过，说明恢复已经执行。

新自检在声音源中断后只泵 200 ms 的 RunLoop，随后同时要求恢复成功、播放头又前进超过 100 ms。
声音源恢复时才重置 host 锚点；Timer 晚到或恢复调用耗时，都占用这同一个窗口，剩下的时间可能不足 100 ms。
因此断言测进了 runner 的调度和调用耗时，而不是单纯验证恢复后的功能。CI 日志没有记录具体哪次调用耗了多久，
不把某个宿主机事件说成已证实的触发源。

本机原样运行 63 项全绿；仅在假声音源的恢复中注入 250 ms 延迟、生产代码完全不变，
便稳定出现同一条失败，且恢复次数的断言仍通过。

## 修复

- `checks/PlayerClock/AudioSourceChecks.swift` 新增有界条件等待：单调时钟限时 5 秒，持续泵真实 RunLoop，条件满足立即结束。
- 播放途中恢复与恢复后的时间推进分开等待；就绪、首次起播、失败停播、手动重试和重新接源也按实际状态等待。
- 保留假声音源的 250 ms 恢复延迟作为回归场景，且手动重试还必须真的推进播放头。
- 仍使用真实 PlayerClock、AVPlayer 和 Timer；保留失败后的重试次数、卸片后不回写两个观察窗口。
  超时仍判失败，不增加自动重跑，也不放宽生产恢复逻辑。

## 验证

- 修复前原样检查：63 项、0 失败；注入 250 ms 延迟后：63 项、1 失败，点名原来的推进断言。
- 条件等待修复后，同一延迟场景：63 项、0 失败。
- 反向验证：保留延迟、临时换回旧的 200 ms 等待 → 63 项、1 失败；停止时 2.1137 s，观察到 2.1260 s，
  恢复次数正确但推进不足。还原等待修复后，再临时撤掉生产 Timer 的恢复调用 → 63 项、4 失败。
  两次都非零退出，变更均在运行结束后自动恢复。
- `/usr/bin/arch -arm64 /bin/bash scripts/check-local.sh player-clock`：全部扫描守卫通过，播放器 63 项、0 失败。

## 教训 / 防回归

异步功能检查要等可观察的条件，并给出失败上限；固定睡眠不能同时承担「等任务完成」和「观察完成后的行为」。
延迟注入必须进常规自检，避免只在快的开发机上验证。
长期约束见 [音频引擎的回归合同](../architecture/audio-engine.md)第五节。
