# 2026-11-11 静帧自检的耗时断言在 CI 上误报：拿「一次解码」当「编 119 帧」的尺子

## 症状

CI 第 5 组的 `still-clip-encode（静帧真实产物）` 偶尔红一项，重跑就过：

```
FAIL [line 266] 解码次数：多出来的 119 帧花了 0.86s（上限 0.73s = 一次解码 0.48s + 0.25s） —— 这张图很可能被逐帧重解了
```

两次：0.86 秒对上限 0.73 秒（#378 的 CI，run 42896808052 第一次尝试；那个 PR 只改了文档、证据 JSON 和两个 Python 脚本），
另一次 0.87 秒对 0.74 秒（协调者转来的数；是哪一轮我没在还留着的日志里找到）。静帧管线没有人动过，同一份代码的 main 是绿的。
它不在 AGENTS.md 写的「已知的偶发」里，每次都要有人去认、去重跑，而且 `check-all` 带红就不能合。

## 根因

这条断言（2026-08-08 加的，[案例](2026-08-08-still-clip-decode-per-frame.md)「性能断言怎么写才不飘」）是：

```
基线 = 生产参数只出 1 帧   ≈ 起进程 + 解一次图 + 缩一次 + 编 1 帧
全程 = 生产参数出满 120 帧
断言：全程 − 基线 ≤ 基线 + 0.25s        （多出来那 119 帧，不许贵过一次解码）
```

**尺子和被量的东西不是一种活。** 左边是「编 119 帧 1080p」（libx264，多线程），右边是「解一次 6000×4500 的 PNG」（主要是单线程）。
当时写的是「两边都随机器一起缩放」——整机变慢时是这样，但这两种活**各自**有多快，在 GitHub 的共享 runner 上并不同进退。
把最近 10 轮 CI 里这一行打印的数取出来（它每次都打印，只是没人看）：

| 一次解码（基线） | 多出来的 119 帧 | 占上限 |
|---:|---:|---:|
| 0.43–0.91 秒 | 0.17–0.75 秒 | 23%–75% |

基线 0.91 秒那一轮边际只有 0.27 秒，基线 0.55 秒那一轮边际 0.54 秒：两个数看不出关系。编码那一侧自己就有 4 倍的浮动，
撞上 0.86 / 0.87 秒就超了「一次解码 + 0.25」。本机（M1）是 0.17 秒对上限 0.72 秒，余量 4 倍，所以写的时候、之后本地跑的时候都看不出来。

顺带的一层：断言叫「解码次数」，可它没有数次数，是拿耗时去**推**次数。能数的东西用时间推，慢机器上就会推错。

## 修复

`checks/StillClipEncode/DecodeOnce.swift`（新文件，从 `main.swift` 里拆出来；脚本的编译清单加上它）。「图只该解一次、缩一次」拆成两条：

1. **数出来的**：生产参数只把 `-loglevel` 换成 `verbose` 真跑一遍，读 ffmpeg 自己在结尾报的输入统计
   （`Input stream #0:0 (video): 1 packets read (…); 1 frames decoded`），必须是 1 个包、1 帧。照片政策、原生政策各数一次。
   不看时间，机器快慢、忙闲都不影响。跑不成、读不出这一行算失败，不当通过。
2. **量出来的**：多出来那 119 帧的边际成本，和**同一次运行里**「同一张图先缩到产物尺寸」的边际成本比。
   小图是大图**无损**缩到产物的尺寸（先转一遍、读出产物多大）：画面一样、尺寸一样，于是这 119 帧的编码活两边一样，
   大图那边多出来的只能是跟着源图大小逐帧重做的活。这条留着是因为有一类数不出来：缩放写到了 `loop` 后面，解码还是一次、缩放成了 120 次。
   第一版图省事从产物里取一帧当小图，CI 一跑就看出不对：编码过的画面再编一遍更便宜，它的边际成本系统性地偏小
   （本机比值 1.3，CI 上大图 0.27 秒对它 0.17 秒），白白吃掉余量；换成无损缩的之后比值是 1.0。

   ```
   上限 = max(小图的边际 × 2.5, 小图的边际 + 0.25s)
   ```

   规则是纯值 `StillMarginalCost`。2.5 倍：正确的实现是 1 倍，本机实测逐帧重解 10–13 倍、逐帧重缩约 6 倍，离两边都有两倍以上；
   加 0.25 秒是给快机器的：边际只有 0.1 秒上下时，倍数那一条太紧。四条命令（大图 / 小图 × 1 帧 / 120 帧）轮着跑三轮、每条取最快的一次；
   第一遍超了先再量三轮、接着取最快的，一阵卡顿正好压在大图那几次上的会被洗掉，真退化每一轮都贵、照样超。

旧的「一次解码 + 0.25s」整个去掉了。生产代码一行没动。

- `scripts/check-still-clip-encode.sh`：62/62 通过（原来 48 项：旧断言换成新的一条，多了两次解码次数和 12 行规则自检）。
  本机连跑五次：大图边际 0.11–0.16 秒、小图 0.11–0.18 秒、上限 0.36–0.44 秒。
- **反向验证**（每条都真的红过，红完恢复）：
  - 把规则改回旧的（`allowance = 一次解码 + 0.25s`）：规则自检红 5 行 —— 两次 CI 误报的数（0.86 对 0.73、0.87 对 0.74）、
    慢 runner 上单边 1.2 倍的抖动两行、2 倍的抖动一行。恢复之后这 5 行都过。
  - **逐帧重解**（生产参数改回 `-loop 1 -framerate 2`、去掉 `loop` 滤镜）：红 4 项 —— ffmpeg 报读了 139–140 个包、解了 123 帧（两条政策各一项）；
    大图边际 5.28 秒、小图 0.42 秒、上限 1.05 秒（超 5 倍，再量一遍照样超）；动图那条照旧报「Option loop not found」。
  - **逐帧重缩**（`loop` 写到缩放前面）：解码次数是 1（数不出来），边际成本红：大图 1.02 秒、小图 0.16 秒、上限 0.41 秒。
- **6 倍退化红、1.2 倍抖动不红**：规则自检里各有快机器、慢机器两行（大图那边贵 6 倍 → 红；慢 1.2 倍、小图那边快 1.2 倍 → 过），不跑 ffmpeg、每次结果一样。
- **慢机器上两边一起慢**（本机，正确的实现）：
  - 整个自检放到后台优先级跑（`taskpolicy -b`，只用能效核；这两组是第一版的小图量的）：大图 1 帧 1.38 秒、边际 0.69 秒；小图边际 0.71 秒；上限 1.78 秒，过。
    一次解码慢了 3.4 倍、编码慢了 5 倍，两个边际的比值还是 1。
  - 16 个死循环抢 8 个核：0.31 对 0.27（上限 0.67）、0.16 对 0.13（上限 0.38），都过。
- `scripts/check-local.sh still-clip-encode`（全部扫描守卫 + 这一项）绿。
- CI（第一版，小图还是从产物里取的那一帧）：`check-all` 绿，这一项在 runner 上是大图 1 帧 0.48 秒、边际 0.27 秒，小图边际 0.17 秒，上限 0.42 秒。
  按旧规则这一轮的上限是 0.73 秒。换成无损缩的小图之后那一轮的数见 PR。

## 教训 / 防回归

- **性能断言的尺子要和被量的东西是同一种活，并且在同一次运行里量。**「两边都随机器缩放」只在两边是同一种活时成立；
  解码和编码、单线程和多线程，在共享的 runner 上各有各的快慢。要比就造一个只差「被怀疑的那件事」的对照（这里是同一张图的小尺寸版）。
- **能数的就数，别拿时间推次数。** ffmpeg 自己报读了几个包、解了几帧；断言叫「解码次数」就该去数它。
- **本机余量 4 倍，不等于 CI 上有余量。** 这条断言每次都把数打印出来，CI 上一直在上限的 23%–75% 之间晃，没人看过。
  对着时间的断言落地之后，要去 CI 的日志里看它实际打印的数，而不是只看本机。
- **「重跑就过」的红要当场把数字记下来。** 第一次误报重跑过了就放过了，第二次才来修。
- 长期约束落在 [定格长期约束](../architecture/freeze-frame.md) 4a2 节。
