# 2026-11-05 官网未正确识别部分中文设备语言

## 症状

打开根域名时，首选语言为 `zh`、`zh-TW`、`zh-HK` 等的设备显示英文。
`navigator.languages` 为空、但 `navigator.language` 是中文时也显示英文。
首选法语而第二首选是德语时会显示德文，和“不支持的首选语言默认英文”的新口径不符。
通过 `?lang=` 手动选的语言未保存，当前路径已匹配时参数也不清理。

## 根因

旧的匹配逻辑只接受部分简中地区码，其他中文一律返回英文；空数组是真值，`||` 没有
回退到 `navigator.language`。遍历整个偏好列表会跳过不支持的首选语言。显式参数只参与
当前跳转，不写本机偏好，且只比较 pathname，忽略需要清理的 query。

## 修复

按第一首选语言的基础代码匹配四个已有版本，所有中文变体进入现有简体中文；不支持的
首选统一英文。语言列表显式检查长度。有效 `?lang=` 保存为本机选择、清理参数并保留
原来的文档路径、查询参数和锚点。明确带语言的链接保持稳定，避免覆盖用户主动打开的版本。

实现仍复用 `src/language.js`，不加云端识别、IP 定位或新的第三方依赖。
长期合同见 [官网设备语言与手动选择](../architecture/skycut-website.md#设备语言与手动选择)。

## 验证

- `tests/language.test.mjs` 的 7 项检查调用实际生产入口，验证浏览器跳转、手动选择和
  本地存储；不只测试语言码纯函数。
- 反向验证：临时换回 main 的旧 `src/language.js`，7 项中 5 项失败，明确显示 `zh`
  回英文、根入口跳错、空语言列表未回退、显式偏好未保存和存储不可用时匹配错误；
  恢复修复后 7 项全部通过。
- 47 项网站测试、生产构建、SEO 产物审计与 `scripts/check-local.sh` 原生扫描守卫全部通过。
  自动化使用浏览器接口替身调用真实生产函数，不冒充已经修改真实设备语言做了人工验收。

## 教训 / 防回归

地区与字形标签必须跟随当前产品的翻译政策，不能把旧网站的严格简中判定当成永久规则。
检查浏览器 API 时要区分缺失、空数组与有效列表；语言选择还要走实际跳转、偏好存储和
深链接路径，不能只靠几个语言字符串单测。分享链接的明确语言与根入口的自动识别分别负责。
