# 2026-11-04 官方生成把确认问题缓存成已完成操作

## 症状

官方生成选择需要批准的规格后，第一次返回 `needs_confirmation`。用户同意、代理带同一个
`idempotency_key` 和 `confirm_token` 重试，仍只拿到旧问题，始终不能启动任务。
每日硬预算不足时的 `blocked` 也会被记住；用户提高上限后，同一操作仍被旧结果挡住。

这是官方接入提交前复审发现的问题。没有重复扣费，但批准和预算解除后的正常流程被卡死。

## 根因

`SkyStudioOfficialGenerateTool.submit` 把预算闸的确认问题直接返回给上层；上层在所有返回后
无条件调用 `SkyStudioGenerationRequests.complete`，没有区分“任务启动”和“等待批准”。

语义摘要正确地排除了 `confirm_token`，因此确认重试应当沿用同一个操作身份；但 `begin` 命中
误存的旧问题后立即返回，既没有重新核对预算，也走不到确认码兑换。单测覆盖了确认码绑定和幂等缓存
各自的规则，原先的后台流程采用不需要批准的草稿规格，漏掉了两者的真实接线。

## 修复

- `SkyStudioGenerationRequests.completeStarted` 仅接收 `status=started` 且有非空本机 `job_id` 的结果。
- 官方新提交统一使用该入口。确认问题与预算阻止保留为未完成占位，由已有 `defer` 清掉，允许同 key
  再次通过当前报价、审查和预算闸。
- 显式准备任务、已启动任务与持久原单恢复继续复用原操作；未知结果不能借此重放收费 POST。
- 生产接线守卫要求官方提交使用 `completeStarted`，禁止在其后重新无条件缓存返回值。

## 验证

- `scripts/check-sky-studio.sh` 新增真实预算闸、确认码、幂等完成策略与 HTTP 适配器联动检查：
  同 key 问题 → 错码拒绝 → 正确确认 → 恰好一次 POST；重复调用不二次预留或 POST。
- 同 key 硬预算阻止 → 提高上限 → 当前确认 → 启动，旧 `blocked` 不被当作完成；缺本机任务号的
  `started` 标签也不能占住操作 key。
- 隔离副本去掉 `completeStarted` 的筛选后，1441 项中 15 项准确失败；保留生产修复，未改共享源码。
  把实际官方入口改回无条件缓存的隔离接线守卫也准确红 2 条。
- 旧 linked App 的真实后台 MCP 反向已红在“同 key 带真实确认码应返回 started”的断言；仍返回旧
  `needs_confirmation`，没有假服务准入任务或真实消费。修复后的后台验收由本轮实施报告记录，尚未完成前不记通过。

## 教训 / 防回归

幂等缓存应保存实际操作的身份，不应冻结改变操作条件的交互问题。确认码被排除在语义摘要之外时，
必须把“同 key 带确认码再次进入真实闸门”作为完整路径验收，不能只分别验证两个纯函数。
