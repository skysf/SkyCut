# 2026-10-18 字幕自动折行把中文的词拆在两行：「快 / 手」「以 / 及」「GPT / Image」

## 症状

测试员转来（测试版 0.18.45，L16 课程的测试工程 `SrtFlow_测试_L16.srtflowproj`，圆体 72 号）：一句放不进一行的中文字幕自动折行时，
「快手」被拆在两行，「GPT / Image」也被拆开。拿生产的 `SubtitleLineWrap` 把这个工程的字幕在不同宽度下折一遍，拆得比报告的还多：

- 「工作区里有三个标签 / 页 图像、视频和音乐」—— 句中现成的空格（去掉的逗号）就在「标签页」后面，却断在「标签」和「页」之间；
- 「视频标签页也提供了 多 / 个目前最强的视频模型！」「OpenAI 的 GPT Image 以 / 及字节跳动的 Seedream」「我们这节课会讲快手和抖 / 音…」；
- 「包括 Google 的 Nano / Banana、…」「…OpenAI / 的 GPT Image…」（「的」跑到行首）。

预览、AI 读的框、成片三处都是这几行（它们同一份折行），所以成片里也这样。

## 根因

2026-10-15 让烧录也能折中文时（[没有空格的长中文字幕成片整行溢出](2026-10-15-chinese-subtitles-overflow-without-spaces.md)），`SubtitleLineWrap`
能起新一行的地方定成「ASCII 空格之后 + **中日文任意两个字之间**」（只管标点避头尾），挑行仍是 libass 的「贪心 + 只看宽度摊匀」：
摊匀时上一行最后一个「词」对中文就是一个字，一次挪一个字，只要两行宽度之差变小就挪。于是：

1. **词没有边界**：「以及」「快手」「标签页」和「多个」在算法眼里都是可以从中间断开的一串字；
2. **断点没有好坏**：句中的空格（中文字幕去标点时逗号换成的空格）、顿号、句号后面，和一个词中间是同一个价钱 —— 只比谁更均匀；
3. **夹在中文里的英文不分轻重**：「Nano Banana」「GPT Image」中间的空格和「的 GPT」前面的空格一样能断。

生成字幕那边（`SubtitleBreaks`）早就按系统分词不切在词中间、按断点好坏挑（`cutCost`），可显示时自动折行是另一条路，没用上。
顺带查到：生成那边的分词把整句一起交给 `NLTokenizer`，**中英文连着写的句子系统会漏掉一大截**（「南极的冰山一望无际Penguins站在风里等待the…」
从「的」到「the」整段一个词都不给），漏掉的那段等于每两个字之间都能切。

## 修复

- `SubtitleCJKWords`（SrtFlowCore，新）：中日文的词在哪只算这一份 —— 字幕折行和生成字幕切条（`SubtitleBreaks.wordBoundaries`）都用它。
  只把汉字 / 假名连成的那几段**各自**交给 `NLTokenizer`（有假名按日文，否则按简体中文；不问 `NLLanguageRecognizer`：一次 1.5 毫秒，
  中英混排时还会认成英文）；分词器中日文各一个、上锁复用；分词漏掉的字各自算一个词。
- `SubtitleRowBreaks`（SrtFlowCore，新）：有中日文的一段，哪儿能起新一行、断在那儿好不好（纯文字）。只在空格之后、中日文的词和词之间断
  （标点避头尾照旧，「5分钟」不拆）；一个词的字之间只给比一整行还宽的词。代价和生成字幕同一张词表（`SubtitleBreakWords`）、同一个量级：
  句中的空格两边都是中文（去掉的逗号）、逗号句号问号后面 −0.6，顿号后面 −0.3；夹在中文里的英文短语中间 +0.3、两个大写开头的词（名字）+0.6；
  助词起头 +1、「的」收尾 +0.4、连词介词代词副词收尾 +1、连词起头 −0.3；数量和名词拆开（「两个 / 平台」）+1；方位词起头（「平台 / 上的」）+0.5；
  单字的词收尾（「短 / 视频」）+0.25、两个单字的词之间（「站 / 在」）+0.3（空格隔开的、收尾的虚词和方位词不算）；日文的助词、助动词起头 +1。
  按整段文字缓存（预览里同一句会反复折）。
- `SubtitleCJKRows`（App，新）：有中日文的段先求**最少几行**能放下（同 libass：断不开的东西比一行宽就让它自己一行），再在这几行里挑
  「摊匀 + 断点代价」最小的折法（摊匀按每行偏离平均的比例的平方，两行时就是生成字幕挑折行点的 2 × imbalance²；一样好时上面的行短）。
  `SubtitleLineWrap` 只把有中日文的段交给它；没有中日文的段（英文、韩文……）照旧是 libass 的 port，一行都不变。
- `SubtitleBreakWords`：不许收尾的词补了「以及、及、或、而、并、还有」和副词、能愿动词（怎么、可以、会、很、都、不、再……），「以及」「还有」
  也算好的起头；加了折行才用的方位词、量词、数词、指示词、日文助词。生成字幕切条也吃这张表（只会让它更不爱把这些词留在一条末尾）。
- AI 读的框（`get_subtitles` 的 `box_note`）改说「在空格处和中日文的词之间折、不拆词」。
- 长期约束写进 [字幕轨可见性与布局](../architecture/subtitle-track-visibility-and-layout.md) 布局第 2 条和人工回归清单、
  [生成的字幕长什么样](../architecture/subtitle-generation-style.md) 第三节第 5 条。

## 验证

- 守卫：
  - `SrtFlowCoreChecks` 的 `SubtitleRowBreakChecks`（新）：中英混排的句子每个汉字都落在某个词里、英文字母不进中日文的词；「以及」「视频」中间
    不是词边界；顿号后面好断、「GPT / Image」「Nano / Banana」贵、「以及」可以起头、「的」起头贵；「5 / 分钟」、行首的「，」、行尾的「（」、行首的
    长音一律不断；句中的空格是这一句里最好的断点；「两个 / 平台」「上的」起头、「怎么」收尾都贵；夹在中文里的英文短语中间有代价。用例只用各版本
    分词都认得的词（CI 和本机 macOS 版本不同），量词那条两种切法（「两个」一个词 / 两个词）都认。
  - `scripts/check-subtitle-burn-size.sh` 的 `WrapChecks`：L16 那几句在 56 / 72 / 96 号 × 0.4–1 个画面宽下（195 种排法）词和「5分钟」都不拆、
    名字 72 号以内不拆（96 号、宽度一半以内四行放不下，只能拆）；两句带空格的断在空格那儿；那句名单断在「、」后面；新加一句真烧的
    （预览 vs 成片按行比左右沿）。原来「100 号四行逐字钉死」是按字摊匀的结果，改成四行、不拆一串词。其余规矩（英文五行、标点插遍每个位置、
    日文、韩文、超长单词、烧录的 ASS）照旧。
- 反向验证（本机：核心库自检 + 只编 WrapChecks 纯算那几组的小程序）：

  2. 去掉「句中空格 = 去掉的逗号」的加分 → 核心库红 2 条、折行规矩红 1 条（断成「工作区里有三个标签 / 页 图像…」：分词把「标签页」切成了两个词）；
  3. 分词改回整句一起交给系统 → 核心库红 1 条（漏掉的正是「的冰山一望无际」「站在风里等待」两截）。
  恢复后核心库 1068 项、折行规矩 31 项全绿。
- PR #248 首跑 CI 第 3 组红：`WrapChecks` 里用了 `checkEqual`，可真烧检查程序（`checks/SubtitleBurnSize/main.swift`）只有 `check`。本地验纯算那几组时

## 教训 / 防回归

- **「能断」和「断在这儿好」是两件事。** 10-15 只解决了「中文能不能折」，用的是渲染器的思路（字和字之间都行、摊匀）；字幕要的是读的人的思路：
  词不拆、断在停顿上。生成字幕早有这一套，显示折行没接上 —— 同一件事（中文在哪儿好断）写了两份，一份对一份不对。
- **系统分词不是总给全的**：中英文连着写时 `NLTokenizer` 会整段不给词。拿它当边界的地方，要么按文字分段喂，要么把漏掉的字当单字词。
- **规则要用真句子在一排宽度上扫**：只看一个宽度时这几句都「看起来还行」；扫 0.4–1 个画面宽、三种字号才把「以 / 及」「GPT / Image」这些都翻出来。
- 分词决定不了的（「字节 / 跳动」「带 / 你」被分词切开），靠「单字收尾」「两个单字之间」这类小代价往回拉；名字、短语要在字号很大、宽度很窄、
  行数又不许加时才会被迫拆开 —— 最少几行是硬的，不为了不拆名字多出一行。
