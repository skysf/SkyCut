# 2026-11-11 预览的音频引擎一直开着：Mac 不会空闲睡眠，App Nap 不生效

## 症状

主窗口的工程只要有过声音，SkyCut 就一直占着声卡，直到退出：

- `pmset -g assertions` 里 coreaudiod 替 SkyCut 挂着 `PreventUserIdleSystemSleep`
  （`com.apple.audio.BuiltInSpeakerDevice.context.preventuseridlesleep`）—— **Mac 不会空闲睡眠**；
- App Nap 不生效（藏起来、闲着，进程优先级也不落到 4）；
- App 里一条优先级 97 的实时线程一直在渲静音，约 0.6% CPU；
- 停着不播也一样；关掉那个工程、主窗口换成空的 Untitled 也一样。

2026-11-11 真实冒烟发现的（[报告](../reports/2026-11-11-voice-real-smoke.md)「发现」第 2 条）。用户同日同意改：
停着一阵子就停掉声音输出、没有声音时立刻停，按播放再起；停过之后第一次播放多等的要听不出来（< 约 0.1 秒）才合。
「一阵子」先定的是约 30 秒；量出来冷着按播放要等声卡 0.15–0.3 秒、到不了 0.1 秒那条线之后，用户当天改定：**约 2 分钟**，
并且用户回到 SkyCut（App 变成活动的、窗口变成主窗口 / 键窗口、鼠标移进窗口、按键）就在主线程外先把引擎起好。

## 根因

三处，都要改才停得下来：

1. **图从不停。** 2026-10-01 音频引擎有意的设计：「暂停 = 锚点标成不播（出静音，图不停）」，第一次重建预览时
   `engine.start()`，之后只有关工程才 `stop()`。当时只量了「播放 / seek 无感」，没量过它对睡眠和 App Nap 的影响。
2. **主窗口换工程不收引擎。** 主窗口那个工程对象不换（`newProject()` / `openProject` 换的是内容）：`closeCurrentDocument`
   只卸片，引擎留着；新工程是空的（重建出来没有合成）时只 `clock.detach()`，上一个工程的图接着开。
3. **播到片尾，引擎还标着「在播」。** 播放器的条目播到头自己停（rate 变 0），没人停声音主时钟：引擎的锚点一直是
   playing —— 播放头照着它一直往后走（越过片尾），而且「停着多久了」永远是 0，停图的规矩永远轮不到它。

查的时候还撞出一处潜伏的错（同一条路，一起修）：

4. **11-05 的恢复按「重启之后采样时间从 0 起」钉锚点**（手动渲染确实如此，自检只在手动渲染上验过连续性）。
   真声卡上 `stop()` / `pause()` 之后再 `start()`，渲染块拿到的采样时间**接着停之前的数往下走**（探针：停 2 秒再起，
   第一拍是 140515、381217……）。锚点写死 0 的话播放头一下跳出去和「图一共开了多久」一样长。11-05 的真声卡回归只断言
   「重启后在往前走」，跳出去也算过。

## 修复

长期约束写在 [音频引擎](../architecture/audio-engine.md) 第二节第 11 条；这里是改了什么。

- **规矩一份**（`AudioEngineIdlePolicy`，纯值）：没有声音的时间线不开图（在播也不开）；在播开着；停着的，最近 2 分钟里
  有人要用声音（刚播完、或者用户回到 SkyCut 有过动作）才开着。
- **照规矩办事**（`AudioEngineIdleKeeper`）：宿主把引擎交给它；换配置之后看一眼、图开着时每 5 秒看一眼、用户回来时看一眼。
  图停着的时候不留计时器。
- **停**（`TimelineAudioEngine.suspend`）：`engine.pause()`，节点、流、播放头、播放状态都留着；喂样线程不再每 50 ms 醒一次。
- **起**：两条路。
  - 用户回到 SkyCut（`AppUserPresence`：SkyCut 变成活动的、它的窗口变成主窗口 / 键窗口、指针移进它的窗口、发给它的
    鼠标和键盘事件 —— 三个通知 + 每个窗口一个一直生效的跟踪区 + 全 App 一个本地事件监视器）→ `wake()` 在后台那条队列上起，
    按播放之前图已经在跑。
  - 时钟要出声时图还停着（第一下就是按播放）→ `recoverIfNeeded()` **当场起**，等声卡起来再从原处开播。
- **锚点不再指望采样时间**（`PlaybackAnchor`）：图刚起 / 停着时发的在播锚点是**待钉**的，第一个渲染块按自己的时间戳原子地
  钉上。图没在跑的时候发的（没有声音的时间线在播）带 host 时间：播放头按 host 时间走，声卡不用开。
- **收**：`unloadPreview()` = 卸片 + 整个引擎收掉；换工程（`closeCurrentDocument`）和时间线空了（重建出来是空的）都走它。
- **片尾**：`PlayerClock` 听「条目播到头 / 播不下去」，停声音主时钟。不看 rate（暂停之后马上再播，rate 的变化晚到一拍）。
- 停图 / 起图各往卡顿日志记一句（不在主线程上写）：对着 `pmset -g assertions` 看得出是哪一下。

### 走过的一条弯路：让播放头先按 host 时间走

第一版照「按下播放不等声卡」做：`wake()` 在后台起，起的那 0.15–0.3 秒里播放头和画面按 host 时间先走，图起来再把声音
接上。引擎单独量很好看（播放头 1 ms 就动）。**放进 App 一量是错的**：冷着按播放，`play()` 3 ms 就回来了，主线程却接着
卡 200 多毫秒 —— 这 250 毫秒里主线程只用了 20 毫秒 CPU，优先级没变。探针查明：**起声卡的那段时间里整个进程的线程一起
被拖住**（一条只读原子数的空转线程也一样；裸 HAL 的 `AudioDeviceStart` 也一样；旁边另一个进程不受影响）。哪条线程起都
救不了界面。于是「先走」换来的只是：界面照样卡这么久，卡完之后画面和声音都已经跳过去 0.2 秒。

改成现在这样：要出声时图还停着就**等它起来再从原处开播**，一帧不少；`wake()` 只留给「用户先动了一下」那条路。

## 验证

机器：MacBookPro17,1（M1），内置扬声器 44.1 kHz，macOS 26.5.2。量的时候机器很忙（别的会话在编译，负载 6–17），
后半段用户还在 Chrome 里放着视频（声卡被它开着）—— 数字偏保守。全程静音（数字静音的素材 + 引擎静音）。

**停过之后第一次播放**（`scripts/check-audio-engine.sh --measure-idle`，从按下起，毫秒，中位 / 最坏 / 最好）：

| 按法 | 画面晚多少（等声卡） | 声音出声卡 | 开头少了多少声音 |
| --- | --- | --- | --- |
| 一直开着（改之前就是这样；5 次） | 0.1 / 0.1 / 0.0 | 25.1 / 25.7 / 17.2 | 0 |
| 回来先有动作、0.25 秒后按播放（图停了 125 秒，5 次） | 0.6 / 17.9 / 0.1 | 21.3 / 34.2 / 17.0 | 0 |
| 冷着按（回来第一下就是播放），图停了 125 秒，5 次 | 258.5 / 269.1 / 222.4 | 280.3 / 292.8 / 245.9 | 0 |
| 参考：回来先有动作、0.25 秒后按（图停了 35 秒，6 次） | 12.3 / 23.1 / 0.4 | 26.8 / 40.9 / 21.9 | 0 |
| 参考：冷着按，图停了 35 秒，6 次 | 268.1 / 295.0 / 144.6 | 287.7 / 310.1 / 159.4 | 0 |
| 参考：冷着按，图停了 2 秒，12 次 | 150.8 / 254.9 / 56.3 | 166.3 / 271.9 / 71.9 | 0 |

App 里（进程内冒烟、debug 构建，8 轮）`PlayerClock.play()` 占主线程：一直开着 0.6 ms、先动一下 0.8 ms（最坏 4.2）、
冷着按中位 217 ms（83–268）。

**结论照实说：冷着按那一种不到「多等 < 0.1 秒」**（画面和声音一起晚约 0.26 秒；一起从原处开始，开头的声音一点不少）；
回来先有过动作的和一直开着一样。用户看过这些数之后定：空闲时长放到 2 分钟、用户回到 SkyCut 就先起 —— 冷着按于是要
同时满足：2 分钟以上没回过 SkyCut（没切过来、没动鼠标、没按键），而且回来的第一下就是空格（SkyCut 一直留在前台、人
走开了两分钟以上再回来按空格；从别的 App 切回来那一下本身就算回来了）。另有一处小代价：隔了 2 分钟以上回来的第一下
动作，界面会顿约 0.1–0.2 秒（后台起声卡拖住进程）。量的时候机器很忙，空闲的机器上应当更短，但这次量不到。

## 教训 / 防回归

- **「一直开着最省事」是有账的，只是不记在自己头上。** 占着声卡 = 整台 Mac 不睡。给一个系统资源写「永远不放」之前，
  去 `pmset -g assertions`、活动监视器的「能耗」里看一眼。
- **引擎单独量出来的数，放进 App 要再量一遍。** 「按下播放不等声卡」在只读原子数的探针里是 1 毫秒，在有界面的进程里是
  250 毫秒：起声卡拖住的是整个进程，不是调用它的那条线程。量主线程卡没卡，要看它这段时间用了多少 CPU（卡着不动和
  忙着干活是两回事）。
- **「重启之后从 0 起」这种话要在真设备上验。** 手动渲染和真声卡不是一个时间域；只断言「在往前走」的回归，跳出去也算过。
- **「在播」要有人收尾。** 谁把状态标成在播，谁就得管它什么时候不在播：播放器自己停下来（片尾）时，主时钟不会自己知道。
- 长期约束：[音频引擎](../architecture/audio-engine.md) 第二节第 10、11 条，第五节的人工回归清单（睡眠断言、App Nap、
  蓝牙耳机上冷着开播要多久这次没量）。
