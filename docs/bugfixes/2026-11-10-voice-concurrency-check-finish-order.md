# 2026-11-10 几批同时交的检查断言了假服务没按住的完成顺序，CI 上偶发红

## 症状

#362（声音 PR 6）推上 ed9dac9 之后，CI 第 1 组的 `scripts/check-voice-recovery.sh` 红了一条：

```
FAIL: the second batch came back before the first ([1, 2, 0, 3])
FAIL: 1 production voice recovery checks
```

其余几十条全过；本机同一棵树连跑多遍（含反向验证的九次）都绿。这条检查是声音 PR 4（#364）随「几批同时交」合进 main 的
`checks/VoiceRecovery/ConcurrencyChecks.swift`，#362 没有改它，也没有改它用到的假服务那几行。

## 根因

场景：四句旁白一句一批、声音池 2 个，假 Sky Studio（`VoiceRecoveryHTTP.deferred`）先回排队、问的时候才回结局；
`holdUntil = [0: 1]` 只按住一对 —— 第一批（第 0 批）要等第二批（第 1 批）回过结局才做完。所以：

- 第 1 批一定比第 0 批先回 —— 这是假服务保证的；
- 第 1 批回来、空出槽，第 2 批才交。之后第 0 批的下一次「问」和第 2 批的「交 + 第一次问」谁先到假服务，**看调度**：
  本机通常第 0 批先（它只差一次 poll 的等待，第 2 批多一个来回），3 核的 CI 虚拟机忙的时候第 2 批先，就成了 `[1, 2, 0, 3]`。

断言写成 `finishOrder.prefix(2) == [1, 0]`，等于额外要求「第 0 批先于第 2 批回来」，假服务从来没保证过这一点。
同一个文件里「一句太长拆成两批」那条也写 `prefix(2) == [1, 0]`，但那个场景只有两批，前两个就是全部，是确定的，不改。

## 修复

`fallbackChecks` 里只断言假服务按住的那一对：第 1 批在 `finishOrder` 里的位置早于第 0 批（缺了任何一个也算红），旁边注释写明为什么
不比别的。其余断言 —— 第 2、3 批带备用的选择、先交的两批不改、`line_models`、落地照原来的顺序、一步撤销 / 重做 —— 只依赖
「第 2 批在第 1 批回来、空出槽之后才交」，这是确定的，不动。

## 验证

反向验证（2026-11-10，每种情形单独改、跑 `scripts/check-voice-recovery.sh`、再恢复）：

| 情形 | 结果 |
| --- | --- |
| A 旧断言 + 临时把 `holdUntil` 改成 `[0: 2]`（第 0 批等第 2 批，确定地逼出 CI 上那个 `[1, 2, 0, 3]`） | 红：`FAIL: the second batch came back before the first ([1, 2, 0, 3])`，和 CI 上那一行一字不差 |
| B 新断言 + 同样的 `[0: 2]` | 绿（整个脚本 PASS） |
| C 新断言 + `holdUntil` 改成 `[1: 0]`（第二批不再先回，`[0, 1, …]`） | 红：`FAIL: the second batch came back before the first ([0, 1, 2, 3])` |
| D 新断言、场景照原样 | 绿（整个脚本 PASS） |

情形 A 说明 CI 上的红就是这个原因，B 说明新断言放过了调度上合理的顺序，C 说明它仍然钉着「后交的先回」。

## 教训 / 防回归

- 并发场景里，假服务按住了哪几对就只断言哪几对；没按住的谁先谁后看调度。要钉更多的顺序，就在假服务里多按住一对（`holdUntil` 多加一项），
  不要靠「本机通常是这样」。
- 本机连跑几遍都绿，证明不了断言不靠时序：CI 是 3 核的虚拟机，调度和本机不一样。写顺序断言前先问一句「假服务保证了这个吗」。
- 长期约束写进了 [Sky Studio 的任务](../architecture/sky-studio-jobs.md)「几批同时交」的检查说明。
