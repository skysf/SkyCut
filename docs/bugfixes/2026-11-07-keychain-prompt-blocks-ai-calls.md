# 2026-11-07 新构建启动弹钥匙串密码框，AI 调用一直等在框后面

## 症状

正式版 0.18.62 启动几秒后出现 SecurityAgent 密码框。第一个 `generate_media` 等了
120 秒没有回答；用户约三小时后输入密码，任务才提交，提交后 28 秒完成。
账号授权和其他不读 Key 的工具仍能回答。原始记录见
[图片模型与角色系统验收](../reports/2026-11-07-image-models-and-characters-smoke.md)「发现」第 1 条。

## 根因

### 两层授权不能混为一谈

正式版的解密访问表信任固定证书和 identifier，每个构建都满足；但自签名证书没有
Team ID，另外的 `partition_id` 仍按 cdhash 记，只含旧构建。固定证书解决 TCC 的
跨版本身份，不保证钥匙串跨构建免输密码。用户目前不购买 Apple 开发者账号，继续保留
每个新构建授权一次的机制，修复的是何时询问和等待方式，不放宽访问表或修改服务名。

### 隔离探针（macOS 26.5.2，arm64）

所有程序、证书材料和驱动放在仓库外临时目录。一次性自签名代码签名证书仅导入专用
临时钥匙串，未读取或改动发布签名目录、钉住的 SHA-1，也未执行创建发布身份的脚本。
测试服务名为唯一的 `com.srtflow.keychain-probe.20261107.<随机值>`，只存假字符串。
输出仅记录状态码、耗时和是否观察到系统框，不输出密钥内容。

探针先校准环境，避免重复旧探针的盲点：

1. `/tmp` 下创建的钥匙串实际版本为 **256**，没有原生分区 ACL；即使手动加入分区
   描述，B 的交互读也直接成功。这些早期尝试不能证明分区授权被拦住。
2. Apple 的 [StorageManager 实现](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_keychain/lib/StorageManager.cpp)
   对用户 `~/Library/Keychains` 下的钥匙串启用受保护格式。因此改用该目录下唯一命名
   的临时文件，实际版本确认是 **512**，其余材料仍在临时目录。
3. A / B 使用同一个证书和 identifier，`codesign --verify -R` 都满足同一 requirement，
   两个构建的 cdhash 不同，Team ID 均未设置。A 建测试项，分区只列 A；访问表保留
   同证书 requirement。用原子替换把 B 放到同一路径，并在进程内核对实际运行的 cdhash，
   防止原地覆盖二进制导致签名缓存混淆。
4. 只读访问表验证 A 在分区名单、B 不在，随后用 B 读同一条。每种读取外部都有 5 秒
   看门狗，只结束本次子进程；不按进程名杀其他 App。

最终 512 格式的结果：

| 读取方式 | OSStatus / 结束方式 | 耗时 | 系统框 |
| --- | --- | --- | --- |
| A 创建 / 首次读取 | 0 / 0 | 约 0.49 / 0.27 秒 | 无 |
| B 只读属性 | 0 | 约 0.26 秒 | 无 |
| B `kSecUseAuthenticationUIFail` 加进程交互关闭 | **−25293**（`errSecAuthFailed`） | 约 0.25 秒 | 无 |
| B 只关闭进程交互 | **−25293** | 约 0.24 秒 | 无 |
| B 只用 `kSecUseAuthenticationUIFail` | 5 秒看门狗终止，未拿到 OSStatus | 约 5.09 秒 | **出现** |
| B 交互读对照 | 5 秒看门狗终止，未拿到 OSStatus | 约 5.19 秒 | 用户确认残留的第二个框 |

结论：原查询标记不足以拦住“访问表通过、仅分区名单不匹配”的密码框；进程交互关闭
能覆盖它。没有用 LAContext 替换文件钥匙串接口。最终测试项删除返回 0，专用钥匙串、
一次性证书及其私钥材料均已清理，发布身份和用户原有 Key 未改动。

**探针操作事故与后续限制**：终止子进程后，两张 SecurityAgent 框仍留在用户屏幕上，
询问临时钥匙串 `skycut-disposable-probe-a2dcfa25ed1af0b60c219166` 的密码。用户误以为
是自己的 Mac 登录密码，输入后无效；协调者随后请用户点了 Deny。**杀进程不等于关掉
已经弹出的系统框**，删除临时钥匙串也不能当作窗口已消失的证据。原来的事前说明只说
可能弹框，没有明确说明这是临时钥匙串密码，造成了混淆。

用户要求之后不再运行任何会弹框的探针或测试，后续验证全部遵守。本机
`check-keychain.sh` 也改为检查进程全程关闭交互，不再运行原生交互读。将来若另获授权
复现系统框，应先明确告诉用户“这是临时钥匙串密码，不是 Mac 登录密码，请点 Deny”；
更优先省掉会弹框的变体，不能用看门狗替代告知和窗口收尾。

### actor 和协作线程也被堵住

旧 `KeychainSecretCache.keyWithoutPrompt()` 在 actor 内同步调用 `SecItemCopyMatching`。
启动的 `/me` 卡在系统框后，actor 无法交出执行权，随后 AI 的付费工具也排在后面。
原来的交互档使用 `Task.detached`，仍占 Swift 协作线程，违反
[阻塞读取约束](../architecture/blocking-media-reads.md)。

## 修复

- `KeychainSecretExecutor` 是全进程唯一的串行 `OperationQueue`。存在检查、读、存、删
  都通过它，原生调用不在主线程或 Swift 协作线程上执行。
- 静默读先保存进程交互状态，再关闭交互；原生调用真正返回后恢复。交互读、写入、删除
  与它互斥，不能在超时回调里提前恢复开关而放出系统框。
- `KeychainSecretCache` 把等待和原生读取分开：静默调用最多等 3 秒；同一次读取仍在
  进行时，其他调用立即回需要授权，不再排队读。超时不强杀原生 Security 调用，迟到成功
  仍缓存；存换删用 generation 废弃旧结果，防止旧 Key 回填。
- 启动先静默试 Key，后台 `/me` 和“再查一次”也只静默读。需要授权时设置保留 Allow，
  并复用主窗口 / 工程窗口的全 App 非模态 notice 挂点，显示更新后的授权提示和按钮。
  真正呈现才按 cdhash 记录，每个构建最多自动提示一次，可关闭，关闭后设置入口仍可用。
- 只有用户的授权按钮进入交互档，界面说明输入 **Mac 登录密码**并选 **Always Allow / 始终允许**，
  只选 Allow 下次启动还会询问。英语、简体中文、西班牙语共用完整文案，手动 upscale 的
  授权提示也使用它。
- AI 付费路径不弹框、不等用户操作，直接给出提示条 / 设置中的 Allow 和 Always Allow
  下一步；`get_status.skycut_plan.keychain_permission=required` 在缓存套餐仍有效时也显示，
  下一步不会被普通购买 / 水印说明覆盖，既有台数限制说明仍保留。套餐和水印规则不变。

## 教训 / 防回归

1. 授权有不同层次。旧的 ad-hoc 访问表探针、256 格式临时钥匙串，都不能代表 512 格式
   的分区名单拒绝；要验证真实触发条件，还要有能证明“本来需要交互”的对照。
2. 查询级的“不显示 UI”标记不等于所有钥匙串实现都遵守。文件钥匙串的进程开关必须
   与所有读写共用串行执行器，并恢复原状态，不能误伤用户主动授权。
3. actor 只负责状态，不承接可能卡线程的系统调用。超时结束的是调用者的等待，原生
   调用仍可能在运行；迟到结果要有清晰的缓存和失效规则，不能宣称已硬中断。
4. **看门狗杀掉测试进程不会关掉 SecurityAgent 框。** 会弹框的探针能省则省；必须做时
   事前明确临时钥匙串密码与 Mac 登录密码不同、请点 Deny，并人工确认窗口收尾。此次
   用户已禁止继续运行此类变体，后续仅运行禁用交互的真实测试和无系统调用的注入用例。
5. 恢复步骤同时写给人和 AI：非模态、可关闭、每构建一次的提示解决“何时问”，明确
   Mac 登录密码和 Always Allow 解决“怎么答”。长期合同和人工清单见
   [Sky Studio 账号](../architecture/sky-studio-account.md)与[签名与系统权限](../architecture/code-signing-and-permissions.md)。
