# 2026-11-04 官方镜头等待名额后仍使用旧提交条件

## 症状

官方生成接入复审发现：首次提交前检查过账户、工程、原始引用和报价，但账户任务已满时，
运行器等 15 秒后会直接再 POST。等待期间关闭工程、更换账户、改写引用或报价到期，
下一次请求仍可能使用旧条件。发现时只做了隔离测试，没有据此发起真实付费重试。

## 根因

检查放在调用任务运行器之前，未覆盖运行器内部的每次提交。`too_many_jobs` 分支还排在
已知任务号处理之前，仅凭错误码判断可重试，可能忽略矛盾的受理 / 计费证据。
退款与回执判断也需要区分“明确未准入”和“已准入但退过款”。

## 修复

每次实际 POST 前运行可选的 `beforeSubmit`，普通路径没有该 hook 时沿用原行为。
官方 hook 重新核对账户 / key、工程注册表及运行代号，再同步检查文件身份、有效期和取消状态。
本机检查拒绝用明确的未提交错误保留原因、释放本机预留并保存 `local_not_sent`，不误报网络丢答。

已知任务号优先进入只 GET 的恢复；只有没有受理或计费证据的明确满额拒绝才能等待后重试。
存在实收、提供方或受理证据时，不能靠错误码覆盖成“从未提交”。未知网络结果继续禁止重放 POST。

## 验证

专项 1,419 项通过：假 HTTP 覆盖每次提交检查、等待中变更、异步检查中取消、
带任务号的容量错误只 GET，以及矛盾的实收 / 退款证据。隔离副本撤掉每次提交 hook 后 12 项失败；
撤掉受理证据保护后 8 项失败。真实工作树保留修复。后台 App MCP 与全量结果记入
[实施报告](../reports/2026-11-04-official-film-client.md)，未执行的步骤不得计为通过。

## 教训 / 防回归

异步等待会使此前通过的条件过期。收费边界的检查必须位于每次真实发送之前，不能只检查外层入口。
明确错误码不能推翻更强的受理 / 账单事实。长期合同见
[官方原创短片](../architecture/official-film.md)「提交回执与恢复」。
