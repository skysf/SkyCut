# 2026-11-02 导出反复解码静止文字和形状

## 症状

用户报告约 104 秒的 1080p 教程导出约 879 秒。使用时长 104.133 秒的教程独立副本，
相同正式默认（1080p、libx264 CRF 23 / slow）重新测得 620.735 秒：准备 18.111 秒，
ffmpeg 602.624 秒。未复现历史 879 秒的精确数值，但慢的主要阶段可以复现。

## 根因

导出图有 107 路输入。文字/形状的静止片段仍经 `OverlayExportFile.append` 写成
`-loop 1 -t <整片长度> -i PNG`；image2 每帧重新解 PNG，即使这一段只显示几秒。
原有静帧工厂早已使用「解一帧、滤镜 loop 复制」，共享叠层接法没有跟着复用。
音频、准备和编码之前的工作只占基线约 3%，单纯改编码器不能解释和解决全部慢速。

## 修复

静止叠层输入只解一次，按工程帧率复制到**本段**长度，加原有两帧接缝余量；时间戳从本段
起点算。仍由同一个 `OverlayExportFile` 接文字和形状，保持 enable 的左闭右开、层序和像素，
不更改正式默认质量。同时增加实际阶段计时，MCP 显式编码/质量和快速审阅预设，后续
不再以总耗时猜阶段。

## 验证

`scripts/check-export-profile.sh` 从真实生产计划和 ffmpeg 日志核对静态 PNG 只解码一帧，
检查真实导出任务的阶段、排队/取消、实际参数、交付尺寸和用户设置保持不变。
完整实测、反向验证和前后画面对账结果见
[导出耗时与快速审阅实测](../reports/2026-11-02-export-profile-review.md)。

## 教训 / 防回归

“一张文件”不等于“只解一次”；重复读取/解码必须量生产命令。已有路径修过的性能规矩，
应让第二个入口复用同一个机制。长期约束在
[文字叠层导出](../architecture/text-overlays.md) 和
[导出设置与计时](../architecture/export-settings.md)，不以降低正式质量掩盖合成开销。
